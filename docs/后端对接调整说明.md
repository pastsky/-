## 一、P0 必须先改（不改会直接报错或状态错乱）

### 1. 角色扩到 7 个

`sys_user.role` 枚举新增：`BRANCH_ADMIN`（分公司管理员）、`VENDOR_ADMIN`（乙方管理员）、`VENDOR_ENGINEER`（乙方检修员）。

- 登录接口返回的 `user.role` 必须是这 7 个值之一；
- 数据权限需要覆盖新增角色：管理端 4 角色全量/按分公司、`VENDOR_*` 按乙方、`VENDOR_ENGINEER` 仅本人被指派 + 池中单；
- 前端菜单与路由已按 7 角色收敛，后端不做隔离也能跑，但会越权。

### 2. 工单状态机（新增状态）

| 状态 | 说明 |
| --- | --- |
| `PENDING_REVIEW` | 待回访（新增） |
| `ESCALATED_FINAL` | 升级终态（新增，仅人工关闭/转线下） |

状态流转最终口径：

```
PENDING --ASSIGN/GRAB--> ASSIGNED --ACCEPT--> PROCESSING --COMPLETE--> COMPLETED(瞬态) --待回访--> PENDING_REVIEW
PENDING_REVIEW --回访满意/评价--> CLOSED
PENDING_REVIEW --完工驳回/回访不满意--> PROCESSING
PENDING / ASSIGNED --RETURN--> PENDING 或入池(pool_flag=1)
PENDING / ASSIGNED / PROCESSING(需客服确认) --CANCEL--> CANCELED
```

**注意 `complete` 的出口变了**：原 `PROCESSING → COMPLETED`，现在完工后业务上进入待回访，请返回 `PENDING_REVIEW`（或返回 `COMPLETED` 同时由服务端立即置为 `PENDING_REVIEW`，二者取一，前端按返回值刷新）。

### 3. `work_order` 新增字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `pool_flag` | TINYINT | 0=常规，1=待抢单 |
| `appointment_time` | DATETIME NULL | 预约时间，NULL 表示「尽快」 |
| `finish_images` | VARCHAR/TEXT | 完工照片，逗号串或 JSON 数组 |
| `finish_remark` | VARCHAR(500) | 完工说明 |
| `elevator_id` | BIGINT NULL | 电梯类工单必填 |
| `community_id` / `building` / `room` | — | 位置快照，创建时落库，后续业主改地址不影响历史单 |
| `escalation_count` | TINYINT DEFAULT 0 | 升级次数，≥2 停止自动升级 |
| `source` | VARCHAR | `USER_REPORT` / `CS_ASSIGN` / `PLAN_TASK` / `INSPECTION` |
| `review_result` | VARCHAR | `SATISFIED` / `UNSATISFIED` / `TIMEOUT_AUTO` |
| `review_remark` | VARCHAR(500) | 回访备注 |
| `reject_count` | TINYINT DEFAULT 0 | 完工驳回次数，上限 3 |

### 4. `work_order_log` 新增 `reason`

- `reason VARCHAR(500)`：退回/转交/驳回/入池原因；
- 必填规则：`RETURN` / `TRANSFER` / `REJECT` / 入池 必填，缺失返回 `1000`；`GRAB` 可空，空则写「抢单」；
- 日志查询接口需同时返回 `operatorName`、`operatorRole`、`reason`（前端时间线展示操作角色）。

### 5. 动作枚举新增

`GRAB`（抢单）、`TRANSFER`（转交）、`REJECT`（完工驳回）、`REVIEW_RESULT`（回访）、`REMARK`（内部备注）。

## 二、P0 接口改动

### 6. 抢单 `POST /api/work-orders/{id}/grab`

- 权限：`ENGINEER` / `VENDOR_ENGINEER`；
- 前置条件：`status=PENDING AND pool_flag=1`，否则 `3000`；
- **状态出口定版：`PENDING → ASSIGNED`**（不是 `PROCESSING`），维修工需再调 `accept`；
- 前置校验 5 类，失败返回明确原因（前端按码提示）：

| 业务码 | 场景 |
| --- | --- |
| `1002` | 数据权限不足 / 账号停用 |
| `3002` | 缺少对应证书（LIFT/ELECTRIC/FIRE 为强制类） |
| `3003` | 当前不在值班状态（`on_duty=0`） |
| `3004` | 存在在途工单未完成（同时仅可处理一单） |
| `3005` | 与该电梯/维修工的预约时间冲突（前后 30 分钟内） |

### 7. 工单池 `GET /api/work-orders/pool`

- 参数：`branchId`、`show_all`、`type`、`priority`、`page`、`pageSize`；
- `show_all=true` 只取消「本小区优先排序」，**不放开抢单权限**；
- 排序：本组单置顶 → 优先级（URGENT 高）→ 创建时间升序；
- 返回项在列表字段基础上增加 `myGroup`、`waitHours`（入池时长，≥4h 前端标超时）。

### 8. 派单 `POST /api/work-orders/{id}/assign`

- 入参 `{assigneeId, remark, priority?}`；
- 同样执行持证/值班/在途/预约冲突校验，失败码同抢单；
- 派单成功后 `pool_flag=0`。

### 9. 推送入池 `POST /api/work-orders/{id}/reassign-to-pool`

- 入参 `{reason, remark?}`，`reason` 必填；
- `PENDING/ASSIGNED` 可入池：`status=PENDING`、`pool_flag=1`、`assignee_id=null`；
- 写 `RETURN` 日志并通知维修工。

### 10. 退回 `POST /api/work-orders/{id}/return`

- **入参新增 `target`**：`REASSIGN`（重新指派）或 `POOL`（入池），`reason` 必填；
- `target=POOL` 时 `pool_flag=1`，否则 `pool_flag=0`；
- 两者都回到 `PENDING`。

### 11. 转交 `POST /api/work-orders/{id}/transfer`

- 入参 `{assigneeId, reason, remark?}`，仅 `PROCESSING` 可用；
- 目标人需通过在途/持证/值班/预约冲突校验；原因必填。

### 12. 完工驳回 `POST /api/work-orders/{id}/reject`

- 入参 `{reason, remark?}`，`COMPLETED` / `PENDING_REVIEW` 可用；
- 回到 `PROCESSING`，`finish_time` 置空，`reject_count+1`；超过 3 次返回 `3000` 并提示走升级督办。

### 13. 回访 `POST /api/work-orders/{id}/review`

- 入参 `{result: SATISFIED|UNSATISFIED, remark?}`；
- 满意 → `CLOSED` + `close_time`；不满意 → `PROCESSING`；
- 写 `REVIEW_RESULT` 日志。

### 14. 完工 `POST /api/work-orders/{id}/complete`

- **请求体改为 `{remark?, images: string[]}`，`images` 必填 1~6 张，缺失返回 `1000`**；
- 落库 `finish_images` / `finish_remark`；
- 详情接口需返回 `finishImages`、`finishRemark`，业主可见。

### 15. 预约审核 `POST /api/work-orders/{id}/audit-appointment`

- 权限：`ENGINEER` / `VENDOR_ENGINEER`（被指派人）；
- 入参 `{approved: 0|1, newTime?, reason?}`；
- `approved=0` 时 `newTime`、`reason` 必填，写入 `appointment_time`；
- 写日志并通知报修人。

### 16. 内部备注 `POST /api/work-orders/{id}/remarks`

- 入参 `{content, images?: string[]}`，图片 ≤3 张；
- **业主不可见**（详情接口对 `RESIDENT` 不返回 remarks）；
- 写 `REMARK` 日志。

## 三、P1 接口（页面已用，缺了页面会空）

### 17. 基础数据

| 接口 | 用途 |
| --- | --- |
| `GET /api/communities` | 小区下拉 |
| `GET /api/elevators?communityId=` | 电梯下拉，需含 `elevatorNo`、`building`、`status`（`ACTIVE`/`MAINTENANCE`/`INACTIVE`） |
| `GET /api/duty-schedules?month=YYYY-MM` | 预约日期置灰依据；无值班日期前端禁用并提示「当天暂无值班人员」 |

### 18. 用户

- `GET /api/users/engineers` 返回项需补：`groupId`、`groupName`、`onDuty`、`validCerts`、`unfinishedCount`、`todayCount`、`overdueRate`（派单面板直接用这些列）；
- `DELETE /api/users/{id}` 语义改为**逻辑停用**（保留历史、不可登录、不可被指派）：不能停用自己、有未完结工单时拒绝；
- 新增 `PUT /api/users/{id}/enable` 恢复；
- 新增 `GET /api/users/groups` 班组列表。

### 19. 列表查询参数与排序

`GET /api/work-orders` 需支持：

`status`、`type`、`priority`、`poolFlag`、`keyword`（工单号/标题/描述/业主姓名/业主电话/电梯编号）、`startDate`、`endDate`、`overdue=true`、`escalated=true`、`page`、`pageSize`。

返回项需补：`poolFlag`、`appointmentTime`、`escalationCount`、`source`、`elevatorNo`、`reporterPhone`、`overdue`。

默认排序：`URGENT` 未完结置顶，其余按创建时间倒序。

### 20. 批量操作 `POST /api/work-orders/batch`

- 入参 `{ids: number[], action: 'pool'|'cancel', reason}`；
- 逐单校验状态，返回 `{success: [...], failed: [{id, orderNo, reason}]}`，前端按失败明细弹窗。

### 21. 统计

| 接口 | 变更 |
| --- | --- |
| `GET /api/stats/workbench` | 新增，返回 `pending/assigned/processing/pendingReview/pool/overdue/escalated/urgent` 计数 |
| `GET /api/stats/overview` | 新增 `pendingReview`、`pool`、`overdue`、`escalated` |
| `GET /api/stats/engineer-performance` | 新增 `groupName`、`overdueRate`（未分组返回「未分组」） |
| `GET /api/stats/export` | 改为**异步任务**，返回 `{taskId, message, expireDays: 7}`，完成后通过站内通知下发链接 |

### 22. 通知与广播

- `POST /api/notifications/broadcast`：入参 `{title, content, targetScope: ALL|ROLE|BRANCH, targetRole?, branchId?, type?}`，返回 `{delivered}`；无匹配接收人返回 `1000`「未匹配到接收人」；
- `GET /api/notifications/broadcast`：广播历史（标题/范围/类型/送达数/时间）；
- 通知类型新增：`MAINT_PROGRESS`、`ANNOUNCEMENT`、`FEEDBACK_RESOLVED`、`CERT_EXPIRING`、`ASSIGN_TIMEOUT`、`PROCESS_TIMEOUT`、`REVIEW_TIMEOUT`。

### 23. 维修日历 `GET /api/work-orders/calendar?month=YYYY-MM&repairerId=`

返回 `[{date, orders: [{id, orderNo, title, type, building, status, priority, start, end, appointmentTime}]}]`，`start/end` 为 `HH:mm`，按 `acceptTime~finishTime` 聚合，30 分钟刻度。

## 四、联调自测清单

1. 7 个角色分别登录，菜单与数据范围正确；
2. 业主报修带预约时间 → 客服派单 → 维修工接单 → 完工（不传图应失败）→ 客服回访归档；
3. 池单：客服推送入池 → 有在途单的维修工抢单应报 `3004` → 空闲维修工抢到后状态为「待接单」；
4. 退回二选一：重派留在待派单，入池后出现在工单池；
5. 预约冲突：同一电梯 30 分钟内两单，第二单派单/抢单返回 `3005`；
6. 完工驳回 3 次后提示走升级；
7. 广播按角色发送，`delivered` 与实际接收人数一致。
