## 1. 项目概述

物业公司内部运维工单管理平台，覆盖物业日常报修/运维工单的全生命周期管理，主要面向四类角色：

| 角色 | 编码 | 说明 |
| --- | --- | --- |
| 业主/住户 | `RESIDENT` | 发起报修工单、查看进度、评价 |
| 客服 | `CUSTOMER_SERVICE` | 受理工单、派单、跟进 |
| 维修工 | `ENGINEER` | 接单、处理、完工 |
| 管理员 | `ADMIN` | 全部权限 + 人员管理 + 报表 |

**本期范围（三大模块）**：核心工单流程、用户与权限、统计报表。  
**暂不包含**：设备台账、巡检计划。

## 3. Git 管理规范（双仓库）

采用**前后端独立双仓库**，通过本文档接口契约解耦。

| 仓库 | 地址约定 | 说明 |
| --- | --- | --- |
| `property-workorder-frontend` | （待定） | Vue3 前端 |
| `property-workorder-backend` | （待定） | Spring Boot 后端 |

### 3.1 分支模型（Git Flow 简化版）

| 分支 | 用途 | 说明 |
| --- | --- | --- |
| `main` | 生产分支 | 只接受 `develop` / `hotfix` 合并，需打 tag |
| `develop` | 开发主分支 | 日常集成 |
| `feature/xxx` | 功能分支 | 从 `develop` 拉出，完成后合并回 `develop` |
| `fix/xxx` | 缺陷修复 | 从 `develop` 拉出 |
| `hotfix/xxx` | 紧急修复 | 从 `main` 拉出，合并回 `main` + `develop` |

### 3.2 提交规范（Conventional Commits）

提交信息格式：`<type>(<scope>): <subject>`

| type | 含义 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修复缺陷 |
| `docs` | 文档变更 |
| `style` | 代码格式（不影响逻辑） |
| `refactor` | 重构 |
| `test` | 测试 |
| `chore` | 构建/工具/依赖 |

示例：

```
feat(workorder): 新增工单列表筛选功能
fix(auth): 修复 token 过期未跳转登录的问题
```

### 3.3 协作约定

1. 每个功能/缺陷一个分支，完成后提交 **Merge Request / Pull Request**，由对方 review 后合并。
2. 后端接口变更（路径、字段、状态码）→ **先更新本文档第 6 节**，再改代码。
3. 前端不得直接改后端接口约定；如字段缺失，先与后端对齐文档。

## 5. 数据模型设计

### 5.1 枚举约定（前后端共享，使用英文编码传输）

#### 工单状态 `work_order.status`

| 编码 | 含义 | 说明 |
| --- | --- | --- |
| `PENDING` | 待派单 | 工单创建后的初始状态 |
| `ASSIGNED` | 待接单 | 客服已派单，维修工未接 |
| `PROCESSING` | 处理中 | 维修工已接单/开始处理 |
| `COMPLETED` | 已完成 | 维修工完工，待关闭/评价 |
| `CLOSED` | 已关闭 | 工单归档（含已评价） |
| `CANCELED` | 已取消 | 报修人或客服取消 |

**状态流转（合法路径）：**

```
PENDING → ASSIGNED → PROCESSING → COMPLETED → CLOSED
   │         │                        │
   └─────────┴────── CANCELED ←───────┘（取消仅允许 PENDING / ASSIGNED 阶段）
```

#### 工单优先级 `work_order.priority`

| 编码 | 含义 |
| --- | --- |
| `LOW` | 低 |
| `MEDIUM` | 中 |
| `HIGH` | 高 |
| `URGENT` | 紧急 |

#### 报修类型 `work_order.type`

| 编码 | 含义 |
| --- | --- |
| `WATER` | 水 |
| `ELECTRIC` | 电 |
| `AIR` | 空调 |
| `LIFT` | 电梯 |
| `FIRE` | 消防 |
| `CLEANING` | 保洁 |
| `SECURITY` | 安保 |
| `OTHER` | 其他 |

#### 用户状态 `user.status`

| 编码 | 含义 |
| --- | --- |
| `ACTIVE` | 启用 |
| `DISABLED` | 禁用 |

## 6. 接口规范（API）

### 6.1 基础约定

| 项 | 约定 |
| --- | --- |
| 接口前缀 | `/api` |
| 协议 | HTTPS（本地开发 HTTP） |
| 数据格式 | `application/json; charset=UTF-8` |
| 认证方式 | JWT，请求头 `Authorization: Bearer <token>` |
| 时间格式 | 字符串 `yyyy-MM-dd HH:mm:ss`（UTC+8） |

### 6.2 统一响应结构

所有接口（含异常）返回如下结构：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | int | 业务码，`0` 表示成功，非 0 表示失败 |
| `message` | string | 提示信息 |
| `data` | object/array/null | 业务数据 |

### 6.3 分页结构

列表接口 `data` 返回统一分页结构：

```json
{
  "list": [],
  "total": 100,
  "page": 1,
  "pageSize": 20
}
```

### 6.4 业务码定义

| code | 含义 |
| --- | --- |
| `0` | 成功 |
| `1000` | 参数错误 |
| `1001` | 资源不存在 |
| `1002` | 无权限 |
| `2000` | 未登录或 token 无效 |
| `2001` | 用户名或密码错误 |
| `2002` | token 已过期 |
| `3000` | 工单状态不允许该操作 |
| `3001` | 工单不存在 |
| `4000` | 用户不存在 |
| `5000` | 系统异常 |

> 约定：HTTP 状态码除正常 `200` 外，`400`=参数错误、`401`=未认证、`403`=无权限、`404`=资源不存在、`500`=服务异常。前端主要依据 `code` 判断业务结果。

## 7. 联调与部署约定

### 7.1 开发环境

| 项 | 前端 | 后端 |
| --- | --- | --- |
| 地址 | `http://localhost:5173` | `http://localhost:8080` |
| 配置 | `VITE_API_BASE_URL=/api` | `server.port=8080` |

### 7.2 跨域与代理

- 开发阶段：前端 Vite 配置 `proxy`，将 `/api` 代理到 `http://localhost:8080`，避免跨域。
- 后端同时开启 CORS（仅开发环境），允许 `localhost:5173`。

```js
// vite.config.js
server: {
  proxy: {
    '/api': { target: 'http://localhost:8080', changeOrigin: true }
  }
}
```

### 7.3 鉴权与 token

1. 登录成功后，前端将 `token` 存入 `localStorage`。
2. 每次请求由 Axios 拦截器自动附加 `Authorization: Bearer <token>`。
3. 收到 `code=2000`（未登录）/`2002`（token 过期）时，前端清空 token 并跳转登录页。
4. 前端通过路由守卫 + 角色字段控制页面/按钮级权限。

### 7.4 接口文档同步

- 后端使用 **springdoc-openapi** 自动生成 Swagger 文档，地址 `http://localhost:8080/swagger-ui.html`。
- 前端可将 Swagger JSON（`/v3/api-docs`）导入 **Apifox** 进行 Mock 和联调。
- 任何接口变更，后端需同步更新本文档第 6 节，并通知前端。

### 7.5 生产部署

| 项 | 方案 |
| --- | --- |
| 前端 | `npm run build` 产出静态文件，由 Nginx 托管，并反向代理 `/api` 到后端 |
| 后端 | 打包 `jar`，`java -jar` 运行 |
| 数据库 | MySQL 8.0，生产独立实例 |
| 配置隔离 | 后端 `application-prod.yml`，前端 `.env.production` |

## 8. 交付与验收约定

1. **接口先行**：后端先按第 6 节定义提供接口（含 Swagger），前端据此开发。
2. **Mock 兜底**：后端接口未就绪时，前端用 Apifox Mock 开发，字段结构必须与本文档一致。
3. **联调验收**：双方按模块逐项联调，联调通过的接口在本文档接口清单打勾标记（`[x]`）。
4. **变更管理**：字段/枚举/状态码变更须双方确认并更新本文档，禁止口头约定。
